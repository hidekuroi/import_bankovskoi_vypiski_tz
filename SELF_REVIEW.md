# Self-review — импорт выписки

## Три главных решения

**1. Сначала запись на устройство, потом запрос. Нет ответа — значит «неизвестно», а не «ошибка».**
- Ключ операции сохраняется в Keychain до первого POST, ключ удаления — до DELETE. Все повторы идут с теми же ключами.
- Если ответ на отправку потерялся, приложение не шлёт файл заново вслепую. Оно спрашивает сервер по ключу (`/imports/by-key`) и только при 404 предлагает повтор, с тем же ключом.
- После перезапуска приложение только сверяется с сервером и само ничего не отправляет.
- «Удалено» показывается только по GET: ответ на сам DELETE двигает операцию максимум до «Удаляем…».
- Если хранилище отказало в записи, файл не уходит: без сохранённого ключа повтор создал бы второй job.

**2. Одно ядро без React Native, проверяемое против настоящего mock.**
- Машина состояний, движок, HTTP-контракт и логгер лежат в `src/core` и запускаются в Node.
- Все ответы сервера проходят через одну функцию (`applySnapshot`). Ревизии только растут, а после запроса на удаление принимаются только `deleting` и `deleted`. Поэтому ни устаревший, ни поздний ответ не откатит экран и не «воскресит» удалённый импорт.
- Тесты гоняют этот же код по HTTP против `createMockServer` из кита и сверяют счётчики mock. Отказы сети (нет соединения, потерянный ответ, поздний ответ, 503) подставляются на стороне клиента. Так каждый сбой из матрицы воспроизводится без ручных шагов.
- Самописное ядро — выбор под масштаб тестового задания: один экран, один импорт, и без лишних зависимостей видно, как устроена логика. В реальном проекте с многими экранами и запросами нужно брать готовые решения: Zustand для состояния приложения и TanStack Query для серверных данных (кеш, опрос, повторы, мутации). Правила остались бы теми же: ключ сохраняется до отправки, ревизии только растут, «удалено» — только по GET. Просто они жили бы поверх этих библиотек, а не в самописном движке.

**3. На устройстве — минимум данных и только на этом устройстве.**
- Запись операции лежит в Keychain/Keystore в режиме `…THIS_DEVICE_ONLY`: ключи, jobId, ревизия, размер и формат. Её нет ни в iCloud, ни в бэкапах (на Android `allowBackup: false`).
- Имя файла, хеш и отчёт на диск не пишутся.
- Копия файла лежит в Caches под случайным id и удаляется сразу после ответа сервера.
- Цена решения: после перезапуска без сети отчёт не виден, пока не вернётся связь. Это осознанный выбор, и он меняется в одном месте: `save()` в `src/core/store.ts`.

## Что упрощено

- Одновременно идёт только один импорт.
- Отправку нельзя отменить посреди загрузки: сервер мог уже получить байты. Зато после ответа 202 импорт можно удалить в любом статусе. Если обработка идёт дольше минуты, экран об этом говорит.
- Если ОС удалила копию до повторной отправки, файл нужно выбрать заново. Сверки нового файла со старым по хешу нет.
- Рост шрифта заголовков ограничен (`maxFontSizeMultiplier`), чтобы на iPhone SE с самым крупным шрифтом кнопки оставались на экране. Обычный текст масштабируется полностью.

## Что сломается первым в проде и как я это замечу

1. **Чтение файла у реальных провайдеров.** Файл из Google Drive или iCloud, ещё не скачанный на телефон, медленный SD-провайдер — на эмуляторе такого нет. Признак: растёт доля отказов `unreadable` и время шага «проверка файла».
2. **Агрессивная очистка Caches** до повторной отправки. Признак: событие `copy_lost`.
3. **Зависшие операции.** Долгие `unknown`, `not_received` или обработка на сервере, неудачные удаления (`delete_failed`), ошибки записи в хранилище (`store_failed`).
4. **Боевой адрес сервера.** В release разрешён только HTTPS (ATS на iOS, без cleartext на Android). Признак: `transport`-ошибки на всех запросах сразу после релиза.

Журнал событий уже построен на закрытом наборе событий и белом списке полей. Его можно отдать в аналитику как есть: имени файла, байтов и сумм в нём нет, это проверяют тесты. Пороги остановки раскатки записаны в release note.

## Как я работал с AI

Код писался вместе с Claude Code. Требования, решения и компромиссы задавал я сам:
- стек;
- Keychain вместо хранилища, которое попадает в iCloud;
- поведение без сети;
- автоматическая проверка `stale_status`;
- что хранить на устройстве.

Сам проверял:
- всю матрицу приёмки вручную на iOS Simulator и Android Emulator, со сверкой счётчиков mock на экране диагностики;
- тот же сценарий на своём iPhone 17 (iOS 26.5.2): всё работает так же;
- вёрстку на iPhone SE с самым крупным шрифтом (размер шрифта правил вручную);
- прогоны `npm run verify` и замечания отдельного ревью по критериям задания. Найденное исправлено: лишние Android-разрешения, гонка в хранилище, запись на заблокированном телефоне, выход из «зависшей» обработки.
